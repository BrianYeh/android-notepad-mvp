## 2. Blocker 1 Acceptance Spec: Google ID Token Verification

### Requirements

- Use an official Google ID token verifier / official Java verifier.
- Do not hand-roll JWT/JWKS validation unless there is an explicit equivalence proof and signature validation tests.
- Validate:
  - JWT signature.
  - `aud == configured Google Web client ID`.
  - `iss in allowed issuers`.
  - `exp > now`.
  - `sub` is present and non-empty.
- `email` must not be primary identity.
- If email is persisted, store only an HMAC/salted hash.
- Missing `GOOGLE_WEB_CLIENT_ID`, missing issuer config, or verifier initialization failure must fail closed.
- Fake verifier must be test-only or local-only.
- Production `BackendApplication` must not switch to a fake verifier by environment flag.

### Error codes

- `UNAUTHENTICATED`
- `INVALID_ID_TOKEN`
- `ID_TOKEN_EXPIRED`
- `INVALID_AUDIENCE`
- `INVALID_ISSUER`
- `INVALID_SUBJECT`

### Acceptance tests

- Valid token accepted.
- Invalid signature rejected.
- Wrong `aud` rejected.
- Wrong `iss` rejected.
- Expired token rejected.
- Missing `sub` rejected.
- Malformed token rejected.
- Missing config fails closed.
- Fake verifier cannot be production runtime.

## 3. Blocker 2 Acceptance Spec: Purchase Ownership / Obfuscated Account ID

### Requirements

- First binder is not sufficient.
- Firestore unique token ownership prevents duplicate use only; it does not prove purchase ownership.
- Android must not compute HMAC using backend pepper.
- Backend must issue or provide an opaque obfuscated account ID after verifying a Google ID token.
- Obfuscated account ID must be derived backend-side from `googleSub` using Secret Manager pepper or equivalent.
- Do not use email, PII, or raw `googleSub` in the obfuscated ID.
- v1.0.7 `BillingFlowParams` must set the backend-issued obfuscated account ID.
- Backend grant requires Play `externalAccountIdentifiers.obfuscatedExternalAccountId` to match the backend-derived value.
- Missing or mismatched `externalAccountIdentifiers` must not grant premium.
- v1.0.6-B `POST /v1/billing/verify` must be non-granting, even if it is also internal-only.
- Same-owner duplicate verify is idempotent.
- Different-owner token use returns `TOKEN_ALREADY_BOUND` or a generic client-safe error.
- `OWNER_MISMATCH` internal detail must not leak unnecessary account information to clients.

### Error codes

- `TOKEN_ALREADY_BOUND`
- `OWNER_MISMATCH`
- `MISSING_OBFUSCATED_ACCOUNT_ID`

### Acceptance tests

- Matching `obfuscatedExternalAccountId` is eligible for grant.
- Mismatch does not grant.
- Missing `obfuscatedExternalAccountId` does not grant.
- First-binder attack does not grant.
- Same-owner duplicate verify is idempotent.
- Different-owner conflict is rejected.
- Android does not contain obfuscation pepper.

## 4. Blocker 3 Acceptance Spec: Acknowledgement / Grant Contract

### Requirements

- Backend acknowledgement is the formal strategy.
- Android must not be the final source of entitlement.
- Grant requires:
  - Play state is grantable.
  - Ownership is verified.
  - Purchase is acknowledged, or backend acknowledgement succeeded.
  - `expiryTime > now`.
- If `acknowledgementState` is pending and v1.0.6-B does not perform real acknowledgement:
  - Return `VerificationPending`.
  - Return `hasPremium=false`.
  - Do not grant.
- Unknown acknowledgement state must fail closed.
- Already acknowledged is idempotent.
- Acknowledgement failure:
  - Does not grant.
  - Writes retry metadata only.
  - Redacts error details.
- v1.0.7 handles real acknowledgement lifecycle.

### Required status / enum behavior

- `VerificationPending` must not map to premium.
- `Unknown` must not map to premium.
- App and backend must fail closed for unknown statuses.

### Acceptance tests

- Unacknowledged purchase does not grant.
- `VerificationPending` does not grant.
- Already acknowledged is idempotent.
- Acknowledgement failure does not grant.
- Unknown acknowledgement state does not grant.
- App mapper does not treat `VerificationPending` or `Unknown` as premium.

## 5. Blocker 4 Acceptance Spec: SubscriptionsV2 Lifecycle Mapping

Grant only when `expiryTime > now`.

### Mapping

- `SUBSCRIPTION_STATE_ACTIVE` -> `Active` -> grant if `expiryTime > now`.
- `SUBSCRIPTION_STATE_IN_GRACE_PERIOD` -> `GracePeriod` -> grant if `expiryTime > now`.
- `SUBSCRIPTION_STATE_CANCELED` -> `CanceledActiveUntilExpiry` or `ActiveNonRenewing` -> grant until `expiryTime`.
- `SUBSCRIPTION_STATE_ON_HOLD` -> `OnHold` -> no grant.
- `SUBSCRIPTION_STATE_PAUSED` -> `Paused` or `OnHold` -> no grant.
- `SUBSCRIPTION_STATE_EXPIRED` -> `Expired` -> no grant.
- Revoked / refund signal -> `Revoked` -> no grant.
- `SUBSCRIPTION_STATE_PENDING` -> `VerificationPending` or `PendingPurchase` -> no grant.
- `PENDING_PURCHASE_CANCELED` -> no grant.
- `UNSPECIFIED` / unknown -> `Unknown` -> no grant.

### Cache rules

`GET /v1/entitlement` may return cached entitlement only if:

- Backend-owned entitlement exists.
- `expiryTime > now`.
- `lastVerifiedAt` is within TTL or within an explicit `maxStale` window.
- Response includes `stale=true` when stale.

Beyond `maxStale` or beyond `expiryTime`, return no premium.
Play API outage must not create new entitlement.

### Trial rules

- Monthly may have `trial10d`.
- Annual has no trial.
- Never infer annual trial.

### Acceptance tests

- Active before expiry grants.
- Active after expiry does not grant.
- Grace before expiry grants.
- Canceled unexpired grants.
- Canceled expired does not grant.
- On hold does not grant.
- Paused does not grant.
- Expired does not grant.
- Revoked does not grant.
- Pending does not grant.
- Unknown does not grant.
- Play outage returns only valid unexpired cache.
- Expired cache clamps to no premium.
- Annual trial is never shown or inferred.

## 6. Package / Product / Base Plan / Offer Allowlist

### Requirements

- Allowed `packageName`: `com.brianyeh.justnotes`
- Allowed `productId`: `just_notes_premium`
- Allowed `basePlanId`s:
  - `monthly`
  - `annual`
- Allowed `(basePlanId, offerId)` pairs:
  - `monthly` / `trial10d`
  - `monthly` / no offer (`offerId == null`)
  - `annual` / no offer (`offerId == null`)
  - `annual` / `trial10d` is not allowed.
- Client request fields are hints only.
- Backend truth must come from Play response.
- Any package, product, base plan, or offer mismatch must not grant premium.

### Acceptance tests

- Wrong package rejected.
- Wrong product rejected.
- Wrong base plan rejected.
- Annual with `trial10d` rejected / no-grant.
- Monthly with no offer accepted when Play response otherwise matches.
- Annual with no offer accepted when Play response otherwise matches.
- Unknown offer rejected / no-grant.
- Client hint mismatch does not override Play response.

## 9. API Contract Acceptance Spec

### POST `/v1/billing/verify`

v1.0.6-B must be non-granting. It may also be internal-only, but internal-only is not a substitute for non-granting behavior.

Request fields:

- `Authorization: Bearer <Google ID token>`
- `purchaseToken`
- `packageName`
- `productId`
- `basePlanId`
- optional `offerId`
- optional `appVersion`
- optional `versionCode`
- optional `deviceLocale`

Response fields:

- `schemaVersion`
- `hasPremium`
- `status`
- `source`
- `productId`
- `basePlanId`
- `offerId`
- `expiryTime`
- `lastVerifiedAt`
- `acknowledgementState`
- `purchaseTokenHash`
- `errorCode`
- `reason`

Must never log raw `purchaseToken`.

Must never grant without:

- ID token verified.
- Package/product/basePlan/offer allowlist passed.
- Ownership obfuscated ID matched.
- Play grantable state.
- Acknowledged or acknowledgement success.
- `expiryTime > now`.

v1.0.6-B acceptance tests must prove that `POST /v1/billing/verify`:

- Does not write a granting entitlement.
- Returns `hasPremium=false` or an explicit non-granting status.
- Cannot make a later `GET /v1/entitlement` return premium.

### GET `/v1/entitlement`

Request requirements:

- Requires `Authorization: Bearer <Google ID token>`.
- Validates the Google ID token with the same verifier rules as other authenticated endpoints.
- Reads entitlement by verified `sub` / derived owner key only.
- Must not accept client-supplied `googleSub`, owner ID, purchase token, or purchase token hash.
- Missing, malformed, expired, wrong-audience, or otherwise invalid ID token fails closed.

Response fields:

- `schemaVersion`
- `hasPremium`
- `status`
- `source`
- `productId`
- `basePlanId`
- `offerId`
- `expiryTime`
- `lastVerifiedAt`
- `stale`
- `purchaseTokenHash`

Rules:

- Unknown and pending statuses fail closed.
- `maxStale` and `expiryTime` clamp premium access.
- Play outage does not create new entitlement.
- A valid cache entry can only be returned to its verified owner.
