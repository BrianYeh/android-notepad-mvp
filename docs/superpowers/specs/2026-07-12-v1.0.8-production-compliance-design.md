# Just Notes v1.0.8 Production Compliance Design

**Date:** 2026-07-12

**Status:** Approved design

**Target:** Google Play Production, first launch in Taiwan

## 1. Goals

Prepare a production-compliance release without changing the verified subscription or RTDN architecture.

- Publish version name `1.0.8` with version code `6`.
- Host Privacy Policy and Terms of Service on GitHub Pages from this repository.
- Make both legal links clickable in the Android app.
- Provide an in-app and public-web path for authenticated account and associated-data deletion requests.
- Give Google Play reviewers reliable, time-bounded access to Premium without asking them to purchase or start a trial.
- Complete the remaining Play Console declarations and store-listing requirements truthfully.
- Keep the first production country limited to Taiwan.
- Enable Managed publishing before the review submission so approval does not immediately make the app public.

## 2. Product Constants and Non-Goals

The existing product configuration remains unchanged:

- Monthly subscription: TWD 33; `trial10d` applies only to eligible users.
- Annual subscription: TWD 330; no trial.
- Existing Google Play Billing, backend purchase verification, entitlement, KMS, Firestore, acknowledgement, and private RTDN behavior remain authoritative for normal users.

This work does not:

- refactor Billing or RTDN;
- change subscription products, prices, base plans, offers, or trial eligibility;
- create a fake Play purchase or synthetic purchase token;
- store a reviewer password, Google ID token, raw email, or purchase token in source control or documentation;
- deploy a new backend revision until implementation and tests have passed review;
- submit for review or make a public rollout without an action-time confirmation.

## 3. Legal Website

### 3.1 Hosting

GitHub Pages will use the existing `BrianYeh/android-notepad-mvp` repository. A dedicated `site/` directory is the only Pages artifact. A GitHub Actions workflow publishes that directory so application source, build outputs, and internal documentation are not exposed as website content.

Canonical URLs:

- Privacy Policy: `https://brianyeh.github.io/android-notepad-mvp/privacy-policy/`
- Terms of Service: `https://brianyeh.github.io/android-notepad-mvp/terms-of-service/`
- Account deletion: `https://brianyeh.github.io/android-notepad-mvp/account-deletion/`

The site will contain a small home page plus separate Privacy Policy and Terms pages. Pages use plain, accessible HTML/CSS with mobile layouts, semantic headings, visible update dates, and no analytics or third-party tracking.

### 3.2 Privacy Policy Coverage

The policy must accurately describe:

- Google Sign-In identity used for authentication and account ownership checks;
- note data stored locally and optional Google Drive `appDataFolder` synchronization;
- Google Play purchase and subscription status processed by the backend;
- encrypted purchase-token storage, KMS use, Firestore entitlement records, RTDN processing, and limited operational logs;
- purposes, retention, security controls, deletion/contact path, and third-party processors;
- that raw purchase tokens, ID tokens, email addresses, Google subjects, and ciphertext are not intentionally written to application logs.

### 3.3 Terms Coverage

The terms must cover service scope, local/Drive data responsibility, subscriptions and Google Play billing, trial eligibility, cancellation and refunds through Google Play, acceptable use, availability, disclaimer/limitation language, changes, termination, and contact.

### 3.4 Android Integration

The existing Privacy Policy and Terms labels become explicit HTTPS links. They open with an Android browser intent and retain the current visual hierarchy. A failed or unavailable browser target must not crash the app.

## 4. Reviewer Premium Access

### 4.1 Rationale

Play review requires credentials that can access all restricted and paid functionality without requiring the reviewer to create an account, make a purchase, or depend on trial eligibility. Creating a fake Firestore purchase would violate the purchase-token and entitlement invariants. A promotional trial can expire or be ineligible. Therefore reviewer access is a separate, narrowly scoped entitlement source.

### 4.2 Identity and Configuration

The backend continues to verify the Google ID token using the existing verifier. For reviewer access it additionally validates the token's verified email claim and email-verification status. The email is normalized and converted to an HMAC-SHA-256 digest using the existing Secret Manager-backed email-hash key; the raw email is not stored or logged.

A Secret Manager configuration contains only reviewer email digests and their expiration timestamps. It is loaded through the existing secret-provider boundary. The configuration is fail-closed:

- missing or malformed configuration grants nothing;
- an expired entry grants nothing;
- an unverified email grants nothing;
- a non-matching digest grants nothing;
- no reviewer identity or digest is emitted in logs.

Reviewer credentials are entered only into Play Console's App access form and, if needed, the Google sign-in UI during validation. They are never committed, copied into project documentation, placed in environment files, or printed to terminal output. The password should be rotated or the grant revoked after review.

### 4.3 Entitlement Model

Add a distinct `ReviewerGrant` entitlement source. It is intentionally separate from `BackendVerified` purchases.

The authenticated `GET /v1/entitlement` read path evaluates the reviewer grant before returning the sanitized entitlement. A valid grant returns a Premium entitlement bounded by the configured expiry. It does not create or mutate:

- purchase-token ownership records;
- Play subscription records;
- acknowledgement state;
- RTDN deduplication records;
- normal Firestore purchase entitlements.

`POST /v1/billing/verify`, Android Publisher verification, acknowledgement, and RTDN handlers are unchanged. Normal users can obtain Premium only from the existing verified purchase flow.

The Android client recognizes `ReviewerGrant` as a backend-authoritative Premium source. It must not convert it into a locally permanent entitlement; foreground refresh, sign-out, identity change, expiry, or backend rejection removes access according to the existing entitlement-refresh rules.

### 4.4 Audit and Revocation

The grant is operationally reversible by removing the digest or advancing its expiry in Secret Manager and deploying/configuring according to the normal backend procedure. Logs may record a generic reviewer-grant decision and request correlation identifier, but no account identifier, digest, token, email, or ciphertext.

## 5. Account and Data Deletion

Google Sign-In creates an app identity through SSO, so the release must satisfy Google Play's account-deletion requirements. The app exposes a prominent link to the public account-deletion page, and that page remains usable after uninstall.

The public page uses Google Identity Services with the existing public Web OAuth client ID. After explicit confirmation, it sends a short-lived Google ID token to an authenticated `POST /v1/account/delete` endpoint. The ID token is never stored by the page or backend. The endpoint accepts requests only from the exact GitHub Pages origin, requires the literal confirmation value `DELETE`, and returns no identity data.

Deletion is fail-closed while a subscription is active, pending, paused, on hold, or canceled but not expired. The page explains that Google Play billing must be canceled separately and that deletion can complete after entitlement expiry. Once all owned subscriptions are terminal (`Expired` or `Revoked`), the backend transaction creates a one-way hashed, 15-minute account-deletion guard and deletes the user's entitlement and owned subscription documents. Subscription writers read the same guard so an overlapping verification or RTDN transaction cannot recreate deleted records; Firestore TTL removes the guard through `accountDeletionGuards.expireAt`. RTDN deduplication records may remain only until their existing 30-day TTL for fraud prevention and reliable delivery handling; they contain no raw purchase token. Local notes remain under device control, while Drive backups remain in the user's own Google Drive account until the user deletes them there.

The endpoint does not cancel a Google Play subscription, weaken token ownership rules, expose raw identifiers, or modify reviewer grants. The Privacy Policy and deletion page explain scope, retention, cancellation prerequisites, and the support fallback.

## 6. Play Console Configuration

The console configuration will use the approved developer contact email for support, IARC, and required declarations. The reviewer account is entered only in App access with English instructions explaining Google Sign-In and where to find Premium functionality.

Planned declarations and listing work:

- App access: restricted functionality; provide reviewer credentials and confirm access to paid features.
- Content rating: complete IARC questionnaire based on the actual note-taking app behavior.
- Target audience: ages 13 and above; no child-directed design or marketing.
- App category: Productivity.
- Data safety: disclose collection/processing consistently with the architecture and Privacy Policy.
- Account deletion: provide the public deletion URL and accurately declare the in-app deletion path.
- Store listing: app name, short description, full description, icon, feature graphic, phone screenshots, support email, Privacy Policy URL, and Terms link where applicable.
- Countries/regions: Taiwan only for the initial Production rollout.
- Ads, Advertising ID, government, financial, and health declarations remain as already saved: no ads, no Advertising ID, not a government app, no financial features, and no health features.
- Production artifact: replace the version-code-5 draft with the signed version-code-6 AAB after all local verification passes.
- Managed publishing: enable before sending the release to review.

Data Safety answers must distinguish user data from purchase metadata and operational security data. Statements in the form, Privacy Policy, backend behavior, and SDK inventory must agree. No declaration is guessed solely to clear a console warning.

## 7. Verification Strategy

### 7.1 Automated Tests

- Backend tests for verified-email extraction, normalization, HMAC matching, expiration, malformed/missing secrets, and non-matching identities.
- Entitlement tests proving `ReviewerGrant` is returned only on the authenticated read path and cannot be produced through purchase verification or RTDN.
- Regression tests proving normal purchase, cancellation, expiry, acknowledgement, ownership mismatch, deduplication, and sanitization behavior are unchanged.
- Android unit/UI tests for parsing the new source, Premium enable/disable behavior, sign-out/refresh, and clickable legal links.
- Backend and browser tests for authenticated deletion, exact-origin CORS, explicit confirmation, active-subscription blocking, terminal-record deletion, idempotency, and no identity leakage.
- Static scans for accidental credentials, raw email values, tokens, and forbidden logging.

### 7.2 End-to-End Checks

- GitHub Pages URLs return HTTPS 200 responses and render correctly on phone and desktop widths.
- A clean install of version code 6 can sign in with the reviewer account and obtain Premium without a Play purchase.
- A different account cannot obtain the reviewer grant.
- Removing or expiring the grant removes Premium after refresh.
- The public deletion page can authenticate without reinstalling the app; a nonterminal subscription is blocked, while a terminal test account can delete associated backend records without exposing identifiers.
- Existing license-tester purchase and RTDN regression evidence remains valid; any code-touching regression suite must pass again before deployment.
- Cloud Run IAM, private RTDN authentication, Secret Manager access, KMS permissions, and public RTDN 501 behavior remain unchanged unless a verified blocking defect requires a separately approved change.

### 7.3 Release Gates

Before uploading the version-code-6 AAB:

1. focused tests pass;
2. backend and Android test suites pass;
3. the full connected Android suite passes on `LocalNotepad_API35`;
4. `codex xhigh/review` has no unresolved blocking finding;
5. signed AAB metadata and signing certificate are verified;
6. legal pages are live and linked from the app and Play Console;
7. Data Safety and App access have been checked against the implementation;
8. no secret or generated crash artifact is staged.

## 8. Rollout and Rollback

The implementation is committed and pushed only after tests and review. Backend changes are deployed first and smoke-tested while normal purchase behavior remains unchanged. Version code 6 is then uploaded to the existing Production draft, release notes are updated, Taiwan is selected, and Managed publishing is enabled.

Sending the release for review and starting a public Production rollout are separate high-impact actions. Each requires a fresh confirmation immediately before the console action.

Rollback options:

- revoke the reviewer grant by removing/expiring its digest;
- route traffic back to the previous verified Cloud Run revision if the new read-path behavior is defective;
- stop before publishing or halt the managed release if console validation exposes a blocker;
- never roll back by weakening IAM, storing credentials, or fabricating a purchase.

## 9. Success Criteria

The design is complete when version code 6 passes regression and review, legal and account-deletion pages are public, reviewer access works without a purchase and fails closed for all other identities, authenticated deletion works only under its terminal-state safeguards, Play Console declarations are internally consistent, the Taiwan Production release is approved under Managed publishing, and no public rollout has occurred without explicit final confirmation.
